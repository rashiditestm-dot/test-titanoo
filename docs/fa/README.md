## ۰۱ / TiTaN چه کاری انجام می‌دهد؟

TiTaN برای ساخت و مدیریت کاربران پروکسی و کانفیگ‌های اتصال است. بک‌اند با **FastAPI** نوشته شده، داده‌ها در **SQLite** ذخیره می‌شوند و **Xray-core** ترافیک واقعی پروکسی را عبور می‌دهد. Nginx ورودی عمومی HTTP را بین پنل و مسیرهای انتقال پشتیبانی‌شده تقسیم می‌کند.

همین مخزن دو نقش اجرایی دارد:

- **پنل اصلی:** نگهداری کاربران، تنظیمات و اشتراک‌ها؛ ارائهٔ داشبورد؛ ارسال کانفیگ کاربران به نودها.
- **نود:** دریافت کاربران همگام‌شده، اجرای سرویس پروکسی و ارسال گزارش مصرف به پنل اصلی.

```text
Browser / compatible client
             │
      Public domain + TLS
             │
           Nginx
             ├── /login, /dashboard, /api/*, /p/*, /s/* → FastAPI → SQLite
             ├── /vl-ws, /vm-ws, /tr-ws                → Xray WebSocket
             ├── /xhttp, /hup                         → Xray HTTP transports
             └── /titan                               → Xray gRPC

Main panel ── configuration sync ──► remote node
Main panel ◄── traffic reports ───── remote node
```

صفحهٔ عمومی اشتراک بخشی از **همین سرویس** است؛ نیازی به نصب فرانت‌اند یا پروژهٔ دوم ندارد.

### ساختار و مسئولیت فایل‌ها

| مسیر | کاربرد |
| :--- | :--- |
| `app/main.py` | مسیر صفحات، APIها، پاسخ‌های اشتراک و اعتبارسنجی درخواست‌ها |
| `app/db.py` | ذخیره‌سازی SQLite، کاربران، نودها، اشتراک‌ها، تنظیمات و رویدادها |
| `app/nodes.py` و `app/routing.py` | اطلاعات اتصال نود، همگام‌سازی، انتخاب مقصد و مسیر جایگزین |
| `app/geo.py` | تخمین مکان از خود نود و یکسان‌سازی اطلاعات کشور و پرچم |
| `app/xray.py` و `app/links.py` | کانفیگ Xray، آمار ترافیک و تولید لینک |
| `app/reality.py`، `app/wg.py` و `app/sskeys.py` | کلیدها و پیکربندی اختصاصی پروتکل‌ها |
| `app/tasks.py` و `app/state.py` | کارهای پس‌زمینه و وضعیت داخل فرایند |
| `templates/` | صفحات ورود، داشبورد، اشتراک عمومی و وضعیت کاربر |
| `static/js/` | ترجمه‌ها، اتصال رابط داشبورد به API و نمایش پرچم‌ها |
| `static/data/countries.json` | کد کشور و نام فارسی و انگلیسی آن |
| `tests/` و `scripts/` | تست‌های رگرسیون، توسعهٔ محلی و ابزارهای بررسی |

<a id="requirements"></a>
## ۰۲ / پیش‌نیازها

### برای توسعه و بررسی رابط و API

- استفاده از Python **۳.۱۱ یا جدیدتر** و محیط مجازی توصیه می‌شود.
- نصب بسته‌های `requirements.txt`.
- پوشهٔ داده با امکان نوشتن.
- مرورگر جدید. Node.js فقط برای بررسی فایل‌های جاوااسکریپت لازم است، نه برای اجرای سرور پنل.

### برای عبور ترافیک واقعی

- باینری سازگار **Xray-core** و پورت‌های قابل دسترس.
- **Nginx** برای مسیرهای HTTP همراه پروژه، یا پراکسی معادل با تنظیمات صحیح.
- دامنهٔ عمومی و خاتمه‌دهی TLS برای لینک‌های HTTPS.
- فضای ذخیره‌سازی دائمی برای دیتابیس هر سرویس.
- برای WireGuard اختیاری: باینری سازگار، دستگاه `/dev/net/tun`، دسترسی `NET_ADMIN`، پورت UDP و تنظیم مسیریابی و NAT میزبان.

> Dockerfile فعلی باینری‌های **Linux x86-64** را دریافت می‌کند و ایمیج بومی ARM در این مخزن ارائه نشده است. در Windows و macOS می‌توان از موتور مناسب Linux/amd64 یا شبیه‌سازی Docker استفاده کرد؛ نصب بومی کامل سرویس پروکسی روی این دو سیستم‌عامل، مسیر بسته‌بندی‌شدهٔ پروژه نیست.

<a id="local"></a>
## ۰۳ / نصب و اجرای محلی

```bash
git clone https://github.com/rashiditestm-dot/test-titanoo.git
cd test-titanoo
python3 -m venv .venv
. .venv/bin/activate
pip install -r requirements.txt
mkdir -p data
export TITAN_DATA_DIR="$PWD/data"
export TITAN_XRAY_CONFIG="$PWD/data/xray.json"
python -m uvicorn app.main:app --host 0.0.0.0 --port 8000 --no-proxy-headers
```

آدرس `http://localhost:8000/login` را باز کنید. رمز دیتابیس تازه **`TiTaN`** است، مگر اینکه پیش از اولین اجرا `TITAN_ADMIN_PASS` را تعیین کرده باشید. رمز خالی پذیرفته نمی‌شود.

در PowerShell محیط مجازی را با `.venv\Scripts\Activate.ps1` فعال و متغیرها را پیش از اجرای Uvicorn تنظیم کنید:

```powershell
$env:TITAN_DATA_DIR = "$PWD\data"
$env:TITAN_XRAY_CONFIG = "$PWD\data\xray.json"
python -m uvicorn app.main:app --host 0.0.0.0 --port 8000 --no-proxy-headers
```

اگر Xray نصب نباشد، پنل در **حالت توسعه یا mock** اجرا می‌شود. رابط و API قابل بررسی‌اند، اما لینک‌ها ترافیک واقعی عبور نمی‌دهند. اجرای Uvicorn به‌تنهایی مسیرهای Nginx مانند `/vl-ws` را نیز راه‌اندازی نمی‌کند. برای آزمایش اتصال واقعی از کانتینر کامل یا ورودی شبکهٔ درست استفاده کنید.

اسکریپت `scripts/dev_run.sh` سرور توسعه را با بارگذاری مجدد اجرا می‌کند. اسکریپت `scripts/fetch_xray.py` باینری Linux x64 را در `/usr/local/bin` نصب می‌کند؛ به دسترسی مناسب فایل‌سیستم نیاز دارد و نصب‌کنندهٔ چندسکویی نیست.

### متغیرهای محیطی

برنامهٔ پایتون **فایل `.env` را خودکار نمی‌خواند**. متغیرها را در محیط فرایند تنظیم کنید، در Docker از `--env-file` استفاده کنید یا آن‌ها را در بخش Variables سرویس Railway قرار دهید. پیش‌فرض‌ها و جزئیات در [مرجع متغیرهای محیطی](../environment.md) آمده است.

<a id="docker"></a>
## ۰۴ / اجرای Docker

```bash
docker build --platform linux/amd64 -t titan-panel .
docker volume create titan-data

# Replace this value locally. Never commit a real password.
export TITAN_ADMIN_PASS='replace-with-a-long-random-password'
docker run -d --name titan --restart unless-stopped \
  --platform linux/amd64 \
  -p 8000:8000 \
  -v titan-data:/app/data \
  -e TITAN_ADMIN_PASS \
  titan-panel
```

- مثال بالا فقط **HTTP محلی روی پورت ۸۰۰۰** را منتشر می‌کند. پیش از توزیع لینک‌های TLS، یک ورودی HTTPS صحیح جلوی سرویس قرار دهید.
- مسیر `/app/data` محل دیتابیس، تصاویر بارگذاری‌شده و پشتیبان‌ها است. هنگام به‌روزرسانی Volume را حذف نکنید.
- برای هر دیتابیس از یک فرایند یا replica استفاده کنید. نودها نباید یک فایل SQLite مشترک داشته باشند.
- پروتکل‌های TCP مستقیم و UDP به پورت‌های جداگانه نیاز دارند. انتشار پورت `8000` به‌تنهایی برای Reality، Shadowsocks، Hysteria2 یا WireGuard کافی نیست.

<a id="railway"></a>
## ۰۵ / دیپلوی روی Railway

۱. پروژه را Fork کنید یا در مخزنی که کنترلش را دارید قرار دهید.

۲. در Railway از همان مخزن یک سرویس بسازید. تنظیمات **Dockerfile** و فرمان شروع موجود در `railway.json` را نگه دارید.

۳. یک Volume دائمی با مسیر **`/app/data`** متصل کنید. اگر مسیر دیگری انتخاب می‌کنید، `TITAN_DATA_DIR` باید دقیقاً به همان مسیر قابل‌نوشتن اشاره کند.

۴. **پیش از اولین اجرا** یک `TITAN_ADMIN_PASS` قوی تنظیم کنید. برای فرم ورود فعلی، مقدار `TITAN_ADMIN_USER` را همان `TiTaN` نگه دارید.

۵. دامنهٔ عمومی بسازید یا دامنهٔ خود را متصل کنید. پورت مقصد تنظیمات شبکه باید با پورت HTTP عمومی کانتینر، یعنی `PORT`، سازگار باشد. پورت داخلی پنل به‌صورت پیش‌فرض `10000` است و Nginx جلوی آن قرار دارد.

۶. پاسخ **`/healthz`** را بررسی کنید. فایل Railway پروژه همین مسیر را با مهلت ۳۰ ثانیه برای بررسی سلامت تنظیم می‌کند.

۷. وارد `/login` شوید، رمز اولیه را تغییر دهید و دامنهٔ عمومی را در تنظیمات ثبت کنید.

۸. یک کاربر آزمایشی بسازید و با کلاینت سازگار، **عبور ترافیک واقعی** را بررسی کنید؛ پاسخ موفق صفحهٔ پنل کافی نیست.

با وجود دامنهٔ عمومی Railway، معمولاً حالت `TITAN_EDGE_HTTP_ONLY` خودکار شناسایی می‌شود. از انتقال‌های مناسب ورودی HTTP مانند WS یا XHTTP استفاده کنید. کارکرد gRPC به پشتیبانی HTTP/2 در تمام زنجیرهٔ پراکسی وابسته است. TCP مستقیم به TCP Proxy جداگانه نیاز دارد و پورت خارجی باید به **همان ورودی داخلی مورد نظر** متصل باشد. ورودی عمومی عادی HTTP/TCP، UDP ارائه نمی‌کند؛ Hysteria2 و WireGuard را برای این مسیر تضمین نکنید.

> **ماندگاری داده ضروری است.** از بین رفتن فایل‌سیستم موقت ممکن است کاربران، اشتراک‌ها، اطلاعات اتصال نود، کلید نشست و کلیدهای Reality و WireGuard را حذف کند. تنظیم مجدد متغیر رمز عبور این داده‌ها را بازنمی‌گرداند.

فایل `render.yaml` برای Render نیز حفظ شده است. از همین کانتینر و مسیر `/health` استفاده می‌کند، اما **دیسک دائمی ایجاد نمی‌کند**. امکانات فعلی ذخیره‌سازی و شبکهٔ میزبان را بررسی کنید و ماندگاری داده را صرفاً به‌دلیل انتخاب یک پلن فرض نکنید.

<a id="dashboard"></a>
## ۰۶ / راه‌اندازی داشبورد

۱. **امنیت:** در «تنظیمات ← امنیت»، رمز اولیه را تغییر دهید. رمز فعلی لازم است؛ در نصب تازه آن را خالی نگذارید.

۲. **دامنهٔ عمومی:** دامنه‌ای را وارد کنید که کلاینت باید به آن متصل شود؛ مسیر اشتراک را در این فیلد نگذارید. پورت عمومی لینک‌ها پشت HTTPS معمولاً `443` است. در صورت خالی بودن دامنه، بک‌اند از اطلاعات درخواست استفاده می‌کند؛ تنظیم صریح آن برای لینک‌های خارجی قابل پیش‌بینی‌تر است.

۳. **زبان:** از «تنظیمات ← عمومی ← زبان پنل» استفاده کنید. انتخاب زبان در مرورگر ذخیره می‌شود و با صفحات ورود و اشتراک مشترک است. نام‌ها، یادداشت‌ها، دامنه‌ها و محتوای کانفیگ ترجمه یا بازنویسی نمی‌شوند.

۴. **کاربر و کانفیگ:** در بخش کاربران یا کانفیگ‌ها، آیکن افزودن را بزنید. نام، پروتکل، روش انتقال، امنیت و نود مقصد را انتخاب کنید.

۵. **محدودیت‌ها:** واحد و مقدار حجم و روزهای اعتبار را تعیین کنید. حجم صفر یا اعتبار صفر یعنی آن محدودیت تعیین نشده است. وضعیت واقعی محدودیت دستگاه، IP و درخواست در بخش محدودیت‌ها توضیح داده شده است.

۶. **اشتراک‌گذاری:** از آیکن کپی اتصال یا QR استفاده کنید. برای چند کانفیگ در یک لینک، بخش اشتراک‌ها مناسب است.

۷. **بررسی:** وضعیت اتصال و همگام‌سازی نود و «ابزارها ← تست اتصال» را بررسی کنید. در دسترس بودن پنل، به معنی کار کردن همهٔ ورودی‌های پروکسی نیست.

پروژه یک حساب مدیر ذخیره‌شده دارد. کنترل‌های افزودن مدیر و سطح دسترسیِ موجود در ظاهر صفحه، پیاده‌سازی کامل چندمدیری یا RBAC نیستند. دکمه‌های راهنمای ورود نیز فقط پیام راهنما نشان می‌دهند؛ سرویس ورود اجتماعی یا بازیابی ایمیلی پشت آن‌ها وجود ندارد.

<a id="subscriptions"></a>
## ۰۷ / راه‌اندازی صفحهٔ اشتراک

نیازی به سرویس دوم، نصب بستهٔ جداگانه یا build فرانت‌اند نیست.

۱. یک یا چند کاربر و کانفیگ بسازید.

۲. وارد «اشتراک‌ها» شوید و «ساخت لینک اشتراک جدید» را انتخاب کنید.

۳. نام اشتراک را بنویسید و کانفیگ‌های کاربران را انتخاب کنید. در صورت نیاز تصویر مخصوص لینک و عنوان پلن را تعیین کنید.

۴. ذخیره کنید. در فهرست اشتراک‌ها می‌توانید لینک کلاینت، لینک صفحهٔ کاربر یا QR را دریافت کنید، انتخاب کانفیگ‌ها را تغییر دهید و لینک را فعال یا غیرفعال کنید.

| آدرس | کاربرد |
| :--- | :--- |
| `/sub/{uid}` | اشتراک شخصی موجود برای هر کاربر |
| `/s/{token}` | اشتراک گروهی؛ مرورگر صفحه را می‌بیند و کلاینت خروجی رمزگذاری‌شدهٔ موجود را دریافت می‌کند |
| `/s/{token}?raw=1` یا `/s/{token}/base64` | دریافت صریح محتوای اشتراک برای کلاینت |
| `/s/{token}/json` | نمایش ساختاریافته یا اشکال‌زدایی موجود |
| `/p/{token}` | صفحهٔ عمومی اشتراک برای کاربر |
| `/p/{token}/data` | دادهٔ مورد استفادهٔ همان صفحه |
| `/status/{uid}` | صفحهٔ عمومی و سادهٔ وضعیت یک کاربر |

صفحه مصرف، انقضا، کانفیگ‌ها و گزینه‌های کلاینت را نشان می‌دهد و هنگام بازگشت به تب یا اتصال دوباره، داده را تازه می‌کند. وقتی لینک گروهی غیرفعال باشد، صفحهٔ کاربر همچنان باز می‌شود، اما آدرس و کانفیگ‌ها ارائه نمی‌شوند و مسیر مخصوص کلاینت **۴۰۳** می‌دهد. غیرفعال کردن لینک اشتراک، یک URI اتصال را که قبلاً جداگانه کپی شده است باطل نمی‌کند؛ آن کار به مدیریت خود کاربر یا کانفیگ مربوط است.

لینک اشتراک و QR را مانند **اطلاعات محرمانهٔ اتصال** نگه دارید. هر کسی که توکن معتبر داشته باشد به صفحه و کانفیگ‌های مجاز آن دسترسی دارد. عنوان پلن فقط یک برچسب نمایشی است و سیستم پرداخت یا صورتحساب ایجاد نمی‌کند.

در لینک چندکاربره، مصرف و سهمیه‌های عددی جمع می‌شوند. صفحهٔ کاربر زودترین انقضای تعیین‌شده را نشان می‌دهد، در حالی که متادیتای فعلی کلاینت آخرین انقضا را اعلام می‌کند. ترکیب کاربران نامحدود و محدود نیز سهمیهٔ مشترک واحد ایجاد نمی‌کند. این منطق‌های موجود در این تغییرات دست‌نخورده مانده‌اند.

<a id="nodes"></a>
## ۰۸ / افزودن و راه‌اندازی نود

### آماده‌سازی سرویس نود

همین ایمیج را به‌عنوان **یک سرویس جداگانه**، با Volume اختصاصی و دامنهٔ عمومی HTTPS اجرا کنید:

```dotenv
TITAN_ROLE=node
TITAN_NODE_NAME=Amsterdam-01
```

در Railway، مقدار `TITAN_NODE_URL` می‌تواند از `RAILWAY_PUBLIC_DOMAIN` گرفته شود. روی میزبان دیگر، آن را روی URL عمومی نود قرار دهید. نود باید Xray و ورودی شبکهٔ فعال داشته باشد؛ اضافه کردن نام آن در داشبورد، سرور تازه‌ای ایجاد نمی‌کند.

### اتصال از پنل اصلی

۱. در «سرورها» آیکن افزودن را بزنید و دامنه یا URL نود را وارد کنید. پورت سفارشی نیز قابل درج است.

۲. «تشخیص خودکار با دامنه» را بزنید. پنل از همان نود اطلاعات شناسایی را می‌گیرد و اطلاعات موجود را در فرم قرار می‌دهد.

۳. مکان را بررسی کنید. اگر قابل تشخیص نبود، شهر و کشور را دستی وارد کنید. کد دوحرفی مانند `NL` یا `AE` کشور و پرچم را دقیق‌تر مشخص می‌کند.

۴. ذخیره کنید. نود تازه‌ای که هنوز اطلاعات اتصال ندارد می‌تواند کلید پنل را خودکار دریافت کند. سپس پنل همگام‌سازی فوری را امتحان می‌کند.

۵. اگر همگام‌سازی آماده نبود، از «کپی همهٔ متغیرها» در پنجرهٔ راه‌اندازی استفاده کنید. مقادیر موجود `TITAN_ROLE`، `TITAN_NODE_TOKEN`، `TITAN_NODE_URL` و `TITAN_MAIN_URL` ارائه می‌شوند. آن‌ها را روی سرویس نود قرار دهید و دوباره دیپلوی کنید.

۶. یک کاربر را به نود اختصاص دهید و وضعیت همگام‌سازی را بررسی کنید. حالت «خودکار» از بین نودهای آنلاین و همگام‌شده با تأخیر اندازه‌گیری‌شده انتخاب می‌کند. اگر نود شرایط لازم برای سرویس‌دهی به کاربر را نداشته باشد، مسیر جایگزین فعلی پنل حفظ می‌شود.

برای ناوگان با تنظیم دستی، یک `TITAN_NODE_SECRET` قوی و یکسان روی پنل و نودهای مورد نظر تنظیم کنید و URL پنل اصلی و خود نود را نیز مشخص کنید. توکن یا کلید مشترک را در اسکرین‌شات، Issue یا Git منتشر نکنید.

> **اتصال اولیه بر پایهٔ اعتماد در اولین استفاده است.** نودی که کلید یا توکن ندارد، می‌تواند با اولین درخواست مالکیت ثبت شود. هنگام آماده‌سازی از آن محافظت کنید یا پیش از عمومی کردنش کلید مشترک یا توکن اختصاصی را تنظیم کنید. مدل احراز هویت نود در این اصلاحات تغییر نکرده است.

### تشخیص مکان چگونه کار می‌کند؟

- نود به‌روز، مکان را از **IP خروجی عمومی خودش** و با سرویس‌های HTTPS GeoIP تخمین می‌زند و از پاسخ شناسایی موجود ارائه می‌کند.
- پنل اصلی از پاسخ **همان نودی که آدرسش وارد شده است** استفاده می‌کند، نه از کشور خود پنل.
- IP حاصل از DNS یک دامنه ممکن است متعلق به CDN یا ورودی مشترک پلتفرم در کشور دیگری باشد. آن IP مدرک مکان سرور اصلی نیست. در ورودی IP عمومی مستقیم، خود همان IP قابل بررسی است.
- مقدار `colo` کلودفلر دیگر به‌عنوان کشور نود یا جایگزین شکست تشخیص استفاده نمی‌شود. مکان نامعلوم به آلمان یا کشور حدسی تبدیل نمی‌شود و ورود دستی در دسترس می‌ماند.
- GeoIP تخمینی است، به‌ویژه در NAT و خروجی مشترک سرویس‌های ابری. **پنل اصلی و همهٔ نودها** را به‌روز کنید؛ نودهای قدیمی ممکن است هنوز متادیتای قبلی را گزارش کنند.
- کشورهای شناخته‌شده پرچم SVG محلی دارند. نام کشور بدون کد نیز در صورت شناسایی به کد تبدیل می‌شود. کشور نامعلوم با پرچم خنثی نشان داده می‌شود، نه پرچم ساختگی یک کشور.

پینگ‌سنج، رفت‌وبرگشت از مرورگر شما را اندازه می‌گیرد؛ کارت نود وضعیت و تأخیر سمت پنل را نشان می‌دهد. هیچ‌کدام کشور سرور را اثبات نمی‌کنند و کیفیت مسیر اپراتور دیگر را تضمین نمی‌کنند.

<a id="clients"></a>
## ۰۹ / کلاینت‌ها

کلاینت‌های فعلیِ صفحهٔ اشتراک:

| تب سیستم‌عامل | کلاینت‌ها |
| :--- | :--- |
| اندروید | v2rayNG، V2Box، Npv Tunnel |
| ویندوز | v2rayN، Hiddify، NekoRay |
| iOS | V2Box، Streisand، Npv Tunnel |

برای v2rayNG، V2Box، Hiddify و Streisand، طرح URL وارد کردن اشتراک در صفحه متصل شده است. برای بقیهٔ گزینه‌های فهرست، لینک کپی می‌شود و راهنمای جای‌گذاری در برنامه نمایش داده می‌شود. اگر باز کردن برنامه ممکن نباشد، راهنمای نصب نشان داده می‌شود؛ مرورگر نمی‌تواند نصب بودن یک برنامه را با قطعیت تشخیص دهد.

دکمه‌های دانلود از آدرس‌های موجود در خود قالب استفاده می‌کنند. در دسترس بودن آن آدرس‌ها و پشتیبانی پروتکل به نسخهٔ کلاینت و صفحهٔ انتشار یا فروشگاه وابسته است. تب بومی Linux یا macOS و سازگاری همهٔ پروتکل‌ها با همهٔ کلاینت‌ها ادعا نمی‌شود.

برای مدیر واردشده، مسیرهای `/api/users/{uid}/wireguard` و `/api/users/{uid}/wireguard.conf` نیز برای کاربر WireGuard وجود دارند. پشتیبانی از فایل `.conf` یا لینک `wireguard://` به برنامهٔ مقصد بستگی دارد.

<a id="configuration"></a>
## ۱۰ / پروتکل‌ها و تنظیمات

| پروتکل | مسیرهای پیکربندی موجود در کد | شرط اجرا |
| :--- | :--- | :--- |
| VLESS و VMess | WS، XHTTP، HTTPUpgrade، gRPC و TCP | ورودی HTTP صحیح؛ برای TCP مستقیم پورت متناظر باید منتشر شود |
| Trojan | WS و TCP | الزامات TLS باید برقرار باشند |
| Shadowsocks | رمزنگاری‌های AEAD و 2022 | پورت مستقیم اختصاصی؛ مسیر HTTP عادی کافی نیست |
| Hysteria2 | کانفیگ و لینک Hysteria v2 | هستهٔ سازگار، گواهی و کلید TLS و UDP قابل دسترس |
| WireGuard | تولید کانفیگ کاربر و سرور و اجرای اختیاری فرایند | باینری سازگار، TUN، دسترسی سیستم، UDP و مسیریابی میزبان |

بک‌اند ممکن است در شرایط ورودی فقط HTTP یا پورت مستقیم غیرقابل دسترس، روش انتقال یا مقصدِ اعلام‌شده در لینک را تنظیم کند. **لینک تولیدشده و پیام مقصد اتصال** را بررسی کنید؛ انتخاب ذخیره‌شدهٔ فرم لزوماً همان ورودی نهایی عمومی نیست.

تنظیمات موجود دیگر شامل دامنه و پورت عمومی، اثر انگشت مرورگر، ALPN، SNI، پارامترهای Fragment در لینک، فیلترهای مسیریابی و بازهٔ پشتیبان‌گیری‌اند. خود کلاینت نیز باید Fragment را پشتیبانی و فعال کند؛ افزودن پارامترها به لینک برای همهٔ کلاینت‌ها کافی نیست.

کانفیگ تولیدشدهٔ Xray را برای تغییر دائمی دستی ویرایش نکنید؛ پنل آن را دوباره می‌سازد. مسیرهای Nginx همراه پروژه، پورت‌های داخلی مشخصی دارند. تغییر متغیرهای `XRAY_*_PORT` به‌تنهایی همهٔ آن upstreamها را بازنویسی نمی‌کند؛ اگر پورت‌ها را تغییر می‌دهید، تنظیمات متناظر Nginx را هم نگهداری کنید.

<a id="troubleshooting"></a>
## ۱۱ / عیب‌یابی

| نشانه | اولین بررسی‌ها |
| :--- | :--- |
| پیام «پاسخ‌گو نبودن برنامه» در Railway | لاگ build و اجرا، فرمان Docker، مقدار `PORT`، پورت مقصد عمومی، `/healthz` و دسترسی نوشتن Volume |
| رد شدن رمز خالی | نصب تازه از `TiTaN` یا `TITAN_ADMIN_PASS` اولیه استفاده می‌کند؛ تغییر متغیر، رمز دیتابیس موجود را بازنشانی نمی‌کند |
| محدودیت تلاش برای ورود | تا پایان زمان اعلام‌شده صبر کنید و درخواست‌های ناموفق تکراری نفرستید |
| خطای ۴۰۳ هنگام ذخیره | Origin مرورگر، دامنهٔ عمومی و هدرهای پراکسی را بررسی کنید؛ احراز هویت یا کنترل Origin را خاموش نکنید |
| باز شدن پنل ولی وصل نشدن کانفیگ | نصب و اجرای Xray، مسیر کامل انتقال، TLS، DNS، دامنه و پورت عمومی و فایروال میزبان |
| باقی ماندن لینک روی پنل | نود هنوز کاربر را دریافت نکرده، همگام‌سازی قدیمی است، نود غیرفعال است یا مسیر انتخابی را نمی‌تواند ارائه کند |
| تشخیص ندادن کشور | دسترسی شناسایی نود، ارتباط خروجی با GeoIP، نسخهٔ نود و خروجی مشترک ابر؛ در صورت نیاز کشور را دستی تعیین کنید |
| پرچم خنثی | کشور یا کد قابل شناسایی نیست؛ کد معتبر وارد کنید و خطای ۴۰۴ فایل‌های `/static/img/flags/` را بررسی کنید |
| باز نشدن کلاینت از صفحه | نصب برنامه، اجازهٔ مرورگر برای باز کردن برنامه، جای‌گذاری دستی لینک و سازگاری نسخه و پروتکل |
| حذف داده یا کلید پس از دیپلوی | Volume وصل نیست، مسیر اشتباه یا غیرقابل نوشتن است، یا مسیر دیتابیس تغییر کرده است |
| ناپدید شدن تصویر پس از بازیابی | فایل پشتیبان دیتابیس، پوشهٔ `data/gallery/` را شامل نمی‌شود؛ آن را جداگانه بازگردانید |

بررسی‌های کاربردی:

```bash
curl -f http://localhost:8000/healthz
docker logs --tail 100 titan
# Use your configured binary/config paths if they differ.
xray run -test -config /usr/local/bin/config.json
```

مسیر `/healthz` در دسترس بودن سرویس را بررسی می‌کند، نه موفقیت اتصال پروکسی. مسیر محافظت‌شدهٔ `/api/connection-test` اطلاعات بیشتری می‌دهد. گزینهٔ `TITAN_DOCS=1` مستندات API را برای محیط توسعهٔ کنترل‌شده فعال می‌کند؛ در استقرار عادی خاموش بماند.

<a id="maintenance"></a>
## ۱۲ / به‌روزرسانی، پشتیبان‌گیری و نگهداری

۱. **نسخهٔ سالم را ثبت کنید:** شناسهٔ commit، digest ایمیج و نسخهٔ Xray را نگه دارید. Dockerfile هنگام build آخرین نسخهٔ هسته را دریافت می‌کند؛ بنابراین build دوباره ممکن است نسخهٔ این وابستگی را هم تغییر دهد.

۲. **پیش از تغییر پشتیبان بگیرید:** پشتیبان دیتابیس را از تنظیمات دانلود کنید. پوشهٔ تصاویر `data/gallery/`، متغیرها و گواهی‌های خارجی را جداگانه نگه دارید. فایل پشتیبان حاوی کلیدها و توکن‌های حساس است.

۳. **Volume را حفظ کنید:** در دیپلوی عادی حذفش نکنید. برای کپی سرد فایل‌ها، سرویس را متوقف یا نوشتن داده را متوقف کنید و کل پوشهٔ داده را بردارید؛ فقط یک فایل SQLite در حال نوشتن را بدون وضعیت WAL کپی نکنید.

۴. **ابتدا روی محیط آزمایشی به‌روز کنید:** وابستگی‌ها را نصب و تست‌های پایین را اجرا کنید.

۵. **پنل و نودها را هماهنگ دیپلوی کنید:** از کد بررسی‌شدهٔ یکسان استفاده کنید. سلامت سرویس، ورود، تغییرات کاربر، همگام‌سازی نود و هر دو نوع پاسخ اشتراک را بررسی کنید.

۶. **با کلاینت واقعی تست کنید:** متصل شوید، حجم کمی داده منتقل کنید، گزارش مصرف و نود یا مقصد واقعی اتصال را بررسی کنید.

۷. **امکان بازگشت را نگه دارید:** ایمیج قبلی و یک پشتیبان آزموده‌شده در دسترس باشند. در صورت نیاز، دیتابیس و تصاویر متناظر را با هم بازیابی کنید.

پشتیبان‌گیری خودکار از فایل دیتابیس به‌صورت پیش‌فرض هر ۲۴ ساعت انجام می‌شود و هفت فایل در `data/backups/` نگه می‌دارد. برای به‌روزرسانی مهم، دانلود صریح و بررسی فایل پشتیبان را انجام دهید و فقط به برنامهٔ زمان‌بندی تکیه نکنید. بازیابی، دیتابیس فعلی را جایگزین می‌کند. دکمهٔ راه‌اندازی مجدد فرایند را می‌بندد و به سیاست restart میزبان یا کانتینر متکی است؛ Uvicorn محلیِ بدون ناظر را باید دوباره دستی اجرا کنید.

```bash
pip install -r requirements.txt -r requirements-dev.txt
python -m pytest
node scripts/check_i18n.js
node scripts/bridge_smoke.js
TITAN_LANG=en node scripts/bridge_smoke.js
python -m playwright install --with-deps chromium firefox webkit
python scripts/check_ui.py
```

بررسی مرورگری، پنل و دیتابیس موقت خودش را اجرا و در پایان متوقف می‌کند. اسکریپت قدیمی `scripts/verify_deploy.py` **داده، رمز عبور و شمارندهٔ تلاش ورود را تغییر می‌دهد**؛ قبل از اجرا آن را بخوانید و از محیط دورریختنی استفاده کنید. این ابزار بررسی سلامتِ فقط‌خواندنی برای تولید نیست. اسکریپت `scripts/smoke_test.py` نیز داده می‌سازد و رمز آن از متغیر مخصوص ابزار، `TITAN_ADMIN_PASSWORD`، قابل تعیین است؛ آن را هم روی دادهٔ آزمایشی اجرا کنید.

<a id="limitations"></a>
## ۱۳ / محدودیت‌های روشن پروژه

- پرداخت، صورتحساب، ثبت‌نام مستقل کاربران، بازیابی ایمیلی، ورود اجتماعی و چندمدیری کامل در این راهنما ادعا نمی‌شوند.
- فیلدهای `max_devices`، `allowed_ips` و `max_requests` ذخیره و اعتبارسنجی می‌شوند، اما **در مسیر فعلی ترافیک Xray اعمال نمی‌شوند**. این رفتار در اصلاحات حاضر تغییر نکرده است.
- بعضی کنترل‌ها و شمارنده‌های قدیمی صرفاً نمایشی‌اند؛ از جمله افزودن مدیر دیگر، برخی گزینه‌های خروجی و بازهٔ گزارش، اعلان‌ها و دکمه‌های جانبی پاک‌سازی یا بررسی پورت. درصد پایداری نمایش‌داده‌شده نیز SLA اندازه‌گیری‌شده نیست.
- آمار لینک چندکاربره، نمایی از کاربران انتخابی است و حسابداری مشترک یا سیستم مالی ایجاد نمی‌کند.
- GeoIP تخمین است؛ مکان دقیق سرور پنهان پشت CDN را نمی‌توان صرفاً از DNS با قطعیت تعیین کرد.
- لینک وارد کردن یا دانلود کلاینت و پشتیبانی هسته باید برای نسخه و دستگاه واقعی بررسی شوند.
- تست‌های ثبت‌شده، رفتار نرم‌افزار و چیدمان مرورگر را پوشش می‌دهند؛ جای آزمایش زندهٔ Railway، VPS یا همهٔ دستگاه‌ها و سیستم‌عامل‌های واقعی را نمی‌گیرند.
